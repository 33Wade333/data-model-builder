# 工程侧细则（安全网参考，不是第一行动依据）

> 来源：案例 15（GitHub 265K 行）+ 案例 17（MovieLens 5480 万行）实测沉淀。正文原则优先，这里只放工程落地细节。

## 一、千万行级建仓性能策略（案例 17 实测：5.8GB / 25 表 / 133 秒）

| 策略 | 做法 | 为什么 |
|---|---|---|
| 源库只读附加 | `ATTACH 'file:source.db?mode=ro' AS src` | 零写入红线的工程保证——引擎直接拒绝对源库的任何写 |
| 关日志提速 | `PRAGMA journal_mode = OFF`（建仓期，验证前恢复） | 建仓中间态不需要回滚保护，日志是最大 IO 开销 |
| 临时空间落盘 | `PRAGMA temp_store = FILE` | 千万行排序/聚合的中间结果远超内存，落盘防 OOM |
| 内存封顶 | `PRAGMA cache_size` 设固定上限（如 256MB） | 不封顶会被大表扫描吃光内存拖垮整机 |
| 上卷聚合 | 粗粒度 DWS 从细粒度 DWS 加总，不重扫明细 | 3383 万行重扫一次约 40 秒，上卷等价且秒级（须交叉验证背书，见正文"同层上卷"） |
| 分批写入 | 单事务 10 万行一批 executemany | 单事务过大：日志膨胀+内存峰值+失败全回滚 |

**判断标准**：百万行以内不用管这些；千万行级必须做；上亿行考虑预过滤进 ODS（但须口径卡留痕过滤条件）。

## 二、探源必查清单（跑脚本，不要手写 SQL）

正文原则一要求"每张表必查"，落地方式是**一条命令**：

```bash
python scripts/probe_source_db.py --url "$SOURCE_DB_URL" --output probe_report.md
```

脚本自动跑完六项并出报告（含问题标注）：

| 检查项 | 报告里的样子 |
|---|---|
| 行数/字段/主键/空值率（含空串） | 逐表字段字典，>10% 标粗、100% 标"可能无用" |
| 枚举全量 | DISTINCT 列出（自动排除日期/唯一标识/ID 类字段） |
| 完全重复行 | "重复行 N 条——业务上'一件事'的边界在哪？需问用户（去重建键而非丢弃）"；>500 万行自动跳过防拖垮源库 |
| 时间范围 + 数据悬崖 | "末年 2023 年只有 58,130 条（前一年 235,004 条）——年份未存满，趋势对比须用同期口径"；识别类型日期/文本日期/unix 时间戳 |
| 孤儿外键 | xxx_id 猜父表（精确名→表名含基词两级），"子表有、父表没有"行数 |
| 跨表重名字段 | 出现在 ≥3 张表的字段名清单——问用户是否同一含义 |

单表库的孤儿外键/跨表重名两项天然无对象，报告为空属正常（不是漏查）。

**查完必做**：把报告里的异常翻译成业务语言问用户（"这字段 28.4% 是空的，业务上代表什么？"），不能自己消化。

## 三、表入库资格（"无出口不入库"的判定流程）

```
源表 → 问用户"这表给谁用？"
  ├─ 用户说得清 + 当前指标用到 → 全量进 ODS
  ├─ 外部 ID 映射类小表（如 imdbId/tmdbId 对照） → 留 ODS 备未来，不加工
  ├─ 用户不知用途 + 指标无一用到 + 体量大 → 不入库，三重留痕：
  │    ① 对话留痕（AI 给判断依据 + 用户追认）
  │    ② 口径卡"不入库"决策行（含依据）
  │    ③ Step 8 终审清单过一遍
  └─ 用户不知用途 但 体量小 → 留 ODS（成本低，未来可能用）
```

案例 17 实例：genome_scores（1847 万行，算法组产物，覆盖 18.9% 电影）→ 不入库；links（86K 行映射）→ 留 ODS。
