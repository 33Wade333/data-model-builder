# 规矩合同（Rules Contract）

> 这是数据建模方法论中所有规矩的权威汇总。当 SKILL.md 的约束不够具体时，以此文件为准。
>
> 分四类：安全规则（不可违反）、质量规则（必须检查）、流程规则（必须按顺序）、命名规则（必须统一）。

---

## 一、安全规则（Safety Rules）

违反 = 事故。没有例外。

### S1. 源库只读
对源业务数据库只执行 SELECT 查询。绝不执行 INSERT/UPDATE/DELETE/DROP/ALTER。
即使用户说"帮我加个字段"，也拒绝——源库改结构是业务系统的权限，不属于数据建模范畴。

### S2. 密码不进 AI 上下文
数据库连接密码不能出现在 AI 模型的对话上下文中。
传递方式：环境变量（如 `SOURCE_DB_PASSWORD`）或 MCP 工具封装。
AI 只引用变量名，不读取也不展示密码值。

### S3. 探查完断开
源库探查完成后断开连接，不留长连接。探查结果保存到本地文件供后续步骤使用。

### S4. 聚合结果可展示，原始行受限
普通用户只能看聚合结果（指标值、分子、分母），不能直接查源表原始行。
管理员可查看原始行用于排查，但需审计日志。

## 二、质量规则（Quality Rules）

产出物生成后必须自检。不通过的要标红，让用户决定是否接受。

### Q1. 以源表真实数据为准
不信设计文档。探源库时必须看真实数据（SELECT 5~10 行），不能只看表结构定义。
文档说字段存"部门编号"实际存"租户编号"的——以实际为准，标红提醒。

### Q2. 无主键 = 脏数据（含源表整表无主键的处理）
没有主键的表是隐患。在 DWD 层源头拦截（WHERE 主键字段 IS NOT NULL），不让脏数据进后面的层。
**源表整表无主键时**（2026-09-19 案例9/10实测）：ODS 原样镜像（豁免主键要求）；DWD 用代理键
（源行号 rowid 或业务复合键）建主键；整行全空的记录在 DWD 拦截（全空=无任何业务信息=脏数据）。

### Q3. 枚举值看真实数据
枚举字段的取值必须用 `SELECT DISTINCT` 列出来，不能只信文档。
**包括整数枚举**——很多源系统用整数做枚举（1=低,2=中,3=高），整数枚举也要列出全部取值并翻译。
列完后问业务方"有没有还没出现但以后会有的值？"。

### Q3a. 枚举含义靠数据推断后，必须向用户复述确认（2026-09-18 案例5实测发现）
业务方答不上枚举含义（"不清楚你看着定"）时，AI 依数据证据推断的含义，**必须把推断明确复述给用户确认**（"我查了数据，判断 3=未成功，对吗？"），确认后才算拍板。
禁止：自定含义后，再拿它当前提去问衍生问题（用户确认的是你的错误框架，口径就悄悄错了）。
实测教训：pay_status=3 真相是"已退款"，AI 推断成"未成功"且未复述确认——退课率/完课率偏差 0.3pp，GMV 侥幸不受影响。
**适用范围扩展同样要确认**（Northwind 实测）：用户"没发生的不管它"是就准时率说的，AI 把它扩展到"实收销售额剔除未发货订单"——推断合理但未经确认，实收比裁判期望低 2.6 万。一句话：**口径的每一次跨指标复用，都要回用户那里过一遍。**

### Q4. 空值率 >10% 标记（含空字符串）
空值率超过 10% 的字段必须标记，说明原因（如"还没接单的工单此字段为空"），并在后续计算中注意排除。
**外键字段空值 >0% 即标红**——即使空值率只有 2%，外键为空意味着记录无法关联，是脏数据。
**空字符串 = 空值**（2026-09-19 案例9实测发现）：真实脏数据常用空字符串''而非NULL——
探源时必须同时查 `IS NULL` 和 `= ''`，否则空值率报 0% 假阴性（案例9速度字段28.4%空串被漏报为0%）。

### Q4a. 100% 空值字段标记
空值率 100% 的字段自动标记为"可能无用"。可能是废弃字段、尚未启用的字段、或数据灌入有误。

### Q5. 口径卡走完 4 步才算定
4 步：用户口述 → AI 举例确认 → 沉淀成口径卡 → 代码实现。
不能跳步。跳了就要返工。
"AI 举例确认"很重要：AI 拿真实数据问"这种情况算不算？那种情况呢？"，业务方一边答一边把口径精确化。

### Q6. 公式合同统一
所有计算路径（语义层、DWS、ADS、看板、智能体）必须用同一套公式。
统一到一个"公式合同"文件。改一处，全部跟着改。
语义层发布前必须跟 DWS 脚本对账。

### Q7. 逐指标三层对账
上线前每个指标三层算一遍：语义层现场算 vs ADS 物化表 vs 看板后端。
三个数字一样才算通过。不一样就找哪一层的公式有偏差。

### Q8. 穷举对账不是抽样
上线前的对账是每个部门、每个维度值、每个指标、每个时间粒度的值全部对，不是抽几个看。

### Q9. 用户实测才算数
自动化测试通过只是"代码层已验证"。用户必须自己点一遍看板、问一遍智能体。
用户说"其实也没改成功"就是没成功，以用户实测结果为准。

## 三、流程规则（Process Rules）

按顺序执行。跳步 = 返工。

### P1. 8 步按顺序走
Step 1 → Step 2 → … → Step 8。每步必须等用户确认才进入下一步。
不要提前做后面的步骤。用户想跳步时，提醒"跳步可能导致返工，确定吗？"

### P2. 每步先理解业务再动数据
前 3 步（业务域、业务流程、表字段）是"理解业务"，后 5 步是"动手建"。
理解不透就动手 = 后面大概率返工。

### P3. 关键时间点业务方口述确认
业务流程中每个关键时间点（比如"合规开始时间""完工时间"）必须让业务方口述确认。
不能 AI 自己猜，不能只看文档。

### P4. 业务流程有分支也要画出来
画业务流程时必须问"有没有不同情况走不同路径？有没有分支？"
每个分支在数据里怎么体现也要说清楚（如 risk_level 字段标记审批路径）。

### P5. 不同业务域维度可能不同
告警域用"租户+部门"，变更域用"系统+部门"。第一步就把每个域的维度定死。
混用 = 后面全部返工。

### P6. 先讨论一步写一步
不要一口气把 8 步全部做完再给用户看。每步做完展示产出物，用户确认后再做下一步。
用户随时可能补充信息、纠正理解。

### P7. 踩坑→实录→手册
每次事故沉淀成文档：什么问题 + 根因 + 怎么解决 + 沉淀了什么规矩。
下次遇到类似情况查手册就能解决。

### P8. 跨会话必写交接文档
跟 AI 的对话会断、会换工具。每次告一段落写交接文档：当前进度 + 未完成项 + 关键决策。
下一个 AI 接手时读交接文档恢复上下文。

## 四、命名与分层规则（Naming & Layering Rules）

违反 = 后期维护困难。

### N1. 表名英文 + 中文备注
表名用英文小写下划线（如 `dwd_alarm_event`），数据库里必须有中文 COMMENT。
界面显示中文名，代码引用英文名。

### N2. 字段 100% 中文注释
每个字段必须有中文 COMMENT。没有注释的表视为未完成。
**SQLite 替代方案**（2026-09-19 案例10发现）：SQLite 无 COMMENT 语法——改用**数据字典表**
（_table_dict 或 data_dictionary）承载全部表/字段中文注释，效果等同。

### N3. 术语全局统一
统一用"重大"不用"重要"，统一用"租户"不用"客户"（如果业务域是告警）。
同名不同义 = 定时炸弹。

### N4. 枚举中文下沉 DWD + 码值分表
枚举值的中文名在 DWD 层下沉（加中文列），不在上层重复翻译。
每种枚举一张独立维表（dim_alarm_level, dim_repair_status），不要搞一张大 codes 表。
**与 L2"无出口不入库"的冲突判词**：无属性的纯枚举登记维表（如机型登记表，只有码值无其他属性、暂无下游消费）可留——它不是分析资产，是**口径登记**（枚举值的权威名册，口径验证时对表用）。九问#3 审阅时确认其登记价值，连登记价值都没有的才删。

### N5. 语义漂移字段要正名
字段名叫 system_name 实际存 tenant_name 的——要正名，连代码一起改。
改之前：搞清影响范围，设回滚底线。建议：ODS 层保持原样，DIM/ADS 层正名。

### N6. ODS 原样照搬，DIM 才改对
ODS 层原样照搬源表字段名，一个字不改。
DIM 层开始加工成正确可用的维表。映射关系在 DIM 层建表脚本里写清楚。

### N7. DWS/ADS 按主题域分表
不要搞一张大宽表装所有业务域的指标。每个主题域独立一张表。
**DWS 存储类型澄清**（2026-09-19 案例10发现）："只存整数"指**禁存率字段**——
计数存 INTEGER、金额/评分合计存 REAL（原生可加指标）、一律不存 _rate/_pct/_ratio 列。

### N8. 一脚本一表
每个加工脚本只负责一张表。不混。命名即分层：fetch_=ODS, refresh_dim_=DIM, refresh_dwd_=DWD, refresh_dwm_=DWM, refresh_dws_=DWS, refresh_ads_=ADS。

### N9. 调度按依赖排先后
上游跑完才放行下游。不要全部挤在凌晨同一时刻。用依赖门禁或时间错峰。

## 五、语义层与智能体纪律（Semantic Layer & Agent Discipline）

来自 2026-09 语义层 v15→v17 实战回流。数据模型建到语义层之后，这些纪律生效。

### L1. 语义层与智能体解耦（架构纪律，最重要）
语义层（数据模型的地盘）只放"业务和数据是怎么回事"：口径边界、表语义（grain/when_to_use）、业务流程、数据访问纪律。
智能体（自己的地盘）决定"怎么干活"：工具路由、调用顺序、回答格式。
**判据：内容里出现具体工具名（如 run_cube）→ 智能体层；描述业务事实/数据含义 → 语义层。**
多代智能体共用编排时，放智能体层的共享编排文件（一处维护），不放语义层——否则数据模型被 agent 层变更绑架（换个工具就要发语义层新版本）。

### L2. 无出口，不入库
写进语义层的任何字段，必须至少有一个工具能读到。
写了但读不到 = 制造"我们已经有规范了"的虚假安全感，是负债不是资产。

### L3. 业务叫法写进表语义
业务上的别名（如把配置合规表叫"组级体检表"）必须写进 when_to_use 等可检索字段——否则智能体检索命中不了，用户按业务习惯提问就落空。
**技巧：把用户可能的完整问法一起写上**（如"组级体检/配置组体检"），检索从擦线命中变满分。

### L4. 发布走确认卡 + 回读断言
语义层发布必须：变更列确认卡给用户签认 → 发布 → **回读断言**（published 唯一、内容实际生效）。
教训：曾出现"发布动作成功但退役未生效，测试指标仍在线上"——没有回读断言，发了等于没发。

### L5. 对账是闸门，不是一次性
三层对账（语义层现场算 vs ADS 物化 vs 看板）不是"跑过一次"就完——数据天天变，**一次性验证会过期**。
对账脚本接进发布闸门：不过不许发。

### L6. 刷新脚本建表自带主键
CTAS（CREATE TABLE AS）建出来的表天生没有主键——每次刷新都会把事后补的主键抹掉。
治本：建表语句后立即 `ALTER TABLE ADD PRIMARY KEY`（用业务键），不靠事后兜底脚本。
**SQLite 注意**：不支持 ALTER ADD PK——改用 CREATE TABLE 时自带 PRIMARY KEY + INSERT INTO...SELECT 模式（效果等同）。

### L7. verified queries：真实问答沉淀为样本
建一张"问题 + 已验证的工具调用"样本表（call 存**工具名+参数，不存 SQL**），智能体遇到类似问题照着做（few-shot）。
种子从真实问答沉淀；测试数据不填（填了就是自己骗自己）。

## 六、分层纪律速查（Layer Discipline）

这是最常被违反也最致命的规矩，单独列出。

| 层 | 允许 | 不允许 |
|---|---|---|
| ODS | 原样照搬源表 | 改字段名、改数据类型、加计算列 |
| DIM | 加工维表、映射修正 | 聚合、打标 |
| DWD | 打判定标签（0/1），一行一条事件 | 聚合、算率、拉宽补维度 |
| DWM | 拉宽补维度列（join 维表加列） | 聚合、打标、算率 |
| DWS | 按粒度聚合，存分子+分母两个整数 | 算率（分子÷分母）、打标 |
| ADS | 算率 + 环比 + prev | 聚合（率是除法不是聚合）、打标 |

**核心**：口径只在 DWD 写一次。DWS 只存整数。ADS 才算率。每层只向下读——可跳层向下（如 DWD 直读 ODS），禁止向上读更晚的层（与 verify_layer_discipline.py 的判定一致）。
